# PR #1とPR #2のOx nativeで時間差が生じる理由

後続の[PR #2単体の30ページVRT確認](PR2_VRT_REPORT.md)で、通常表示120画像全ての不一致と追加24操作状態のUI欠落を確認した。以下の速度差調査はそのVRTの前に行った診断記録である。

2026-10-31。PR #1の**Ox native互換版**とPR #2の最小テーマを、同じM1 Pro / Node22.22.2 / Ox3.4.3 / Vue3.5.25 / Vite7.3.1で調べた。ここでいうPR #1はNuxt基準や旧Ox単独構成ではなく、前回55.65秒と報告した実装を指す。

**主因は、クライアントJSの大量生成、MDC互換のための本文の重複変換、細かいVue/MDCノードのSSRである。** 出力をPR #2と同じ1,342 Markdown URLに絞っても約52秒かかる。クライアントのMarkdownモジュール生成を省く診断では約36秒まで短くなった。既存表示の維持に加え、現在のパイロット実装の重複処理が時間を増やしている。

## 同じ環境・計測境界での再計測

元ソースはPR #1 `ab4eec5`、PR #2 `c52b733`。独立したgit archiveチェックアウトへ同じ診断フックを追加し、各3回を順次実行した。全12回でHTML件数と元のverifyが成功した。追加CPU採取1回も成功した。通常サイトのコードとVRT基準は変更していない。

| 診断対象 | HTML数 | 1回目 | 2回目 | 3回目 | 中央値 | ピークRSS中央値 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| #1：互換版・全公開URL | 1,991 | 56.038秒 | 52.655秒 | 53.495秒 | **53.50秒** | 3,709 MiB |
| #1：生成対象をMarkdown URLへ限定 | 1,342 | 50.033秒 | 52.451秒 | 53.054秒 | **52.45秒** | 3,260 MiB |
| #1：さらにMarkdownのクライアント生成を省く | 1,342 | 35.780秒 | 36.858秒 | 36.170秒 | **36.17秒** | 3,310 MiB |
| #2：最小テーマ | 1,343 | 4.080秒 | 4.428秒 | 4.465秒 | **4.43秒** | 658 MiB |

今回はNodeプロセス内でViteのimport前からawaitしたbuild完了までを測る。前回のPNPM起動込み55.65秒・5.37秒とは時間境界が異なる。前回の記録は変更せず、工程の比較には今回の同じrunner同士を使う。出力HTMLの列挙・検証はbuild時間の外。OSキャッシュは保持し、コールドディスク性能は測っていない。

Markdown限定版と#2のMarkdown部分は**同じ1,342 URL**であることを集合比較した。#2だけ別途索引1ページを生成する。#1の限定版は、原稿全件のデータ準備と既存部品の依存関係を維持して出力ルートを減らした診断である。固定ページ用の依存まで除去したMarkdown専用アプリの性能を示すものではない。

クライアント生成省略版は、Markdownモジュールのimport一覧だけを空にし、サーバー側の本文処理を維持した。ブラウザーでの本文hydrationが成立しないため、**原因を分けるための診断値**であり、表示互換を満たす移行案ではない。今回VRTは実施していない。

## 約49秒の差の内訳

各構成で中央値に該当した1回（#1は3回目、#2は2回目）の、重ならない区間を集約した。区間の合計が各runのbuild時間に一致することを検証した。GC・parser・transformの小区間はこの表に含まれるため、後から加算しない。

| 工程 | #1・全件 | #2・最小テーマ | 差 |
| --- | ---: | ---: | ---: |
| 起動・設定・ホスト部品読込 | 4.85秒 | 0.35秒 | 4.50秒 |
| クライアントJS/CSS生成 | 19.21秒 | 1.34秒 | 17.86秒 |
| 原稿・ナビゲーション準備 | 5.67秒 | 0.26秒 | 5.41秒 |
| MarkdownのSSRモジュール変換・評価 | 11.69秒 | 2.02秒 | 9.67秒 |
| Vue SSR | 7.76秒 | 0.10秒 | 7.66秒 |
| アセット参照・HTML/payload組立 | 3.11秒 | 0.16秒 | 2.95秒 |
| その他・最終書出し | 1.22秒 | 0.20秒 | 1.02秒 |
| 合計（丸め前を集計） | **53.50秒** | **4.43秒** | **49.07秒** |

`ctx.loadModule()`の時間にはViteによる初回の変換・コンパイル・評価と、その中のMDC処理が入る。単なるディスク読出し時間ではない。

## 1. 本文のクライアントモジュールを全件生成する

[#1のclient.ts](ox-native/client.ts)は`virtual:ox-native-documents`をimportする。[Vite設定](ox-native/vite.config.ts)は公開Markdownごとに動的importを生成する。Viteはそれらをすべてビルドするため、動的importでもビルド時の変換コストはかかる。[互換アダプター](ox-native/markdown-compat.mjs)は本文をMDC ASTのJSONとしてモジュールへ格納する。

| 生成物 | #1・全件/Markdown限定 | #1・Markdownクライアント生成省略 | #2 |
| --- | ---: | ---: | ---: |
| JSファイル数 | 1,252 | 4 | 1 |
| JS合計（圧縮前） | 25,833,876 bytes | 1,646,159 bytes | 1 byte |
| CSS合計 | 184,423 bytes | 184,423 bytes | 465 bytes |

#2の1 byteのJSは最小ビルドの空の成果物であり、本文のクライアントhydrationは行わない。Vueを使ったHTML生成はサーバー側で完了する。#1の生成省略実験で**52.45→36.17秒（約16.3秒短縮）**となったことから、本文のクライアントモジュール生成が大きな負荷であることを確認できた。差には後段のGC等への影響も含まれ、これをコンパイラ単体の所要時間とは扱わない。

## 2. 同じ本文を3経路で処理している

#1は次の経路を持つ。

1. [prepareFullData](shared/full-data.mjs)が全1,434 MarkdownをOx＋MDC互換ASTへ変換し、説明・TOC・style・ナビゲーション等を準備する。
2. クライアントビルドで、公開対象の**1,247ユニークMarkdownファイル**を公式Ox Vueプラグイン＋互換アダプターで再変換する。
3. Custom HostのSSRモジュール読込でも同じ1,247ファイルを再変換する。言語別名による複数URLはモジュールキャッシュを共有する。

互換ASTを組み立てる`nativeDocument`は**1,434＋1,247＋1,247＝3,928回**実行された。MDC parser呼出しはクライアント4,585回、データ準備5,170回、SSR側4,585回、計**14,340回**。全件データ準備にはYAML内のMarkdown 200文字列も含む。#2にはこのMDC互換経路がない。

代表runで公式`ox-content:vue-transform`フックはクライアント0.223秒・SSR側0.267秒だった。一方、その後の互換アダプターはそれぞれ4.451秒・4.976秒。さらにViteのモジュール処理やGCが親工程に含まれる。これらの非同期フック・parserの合算値は重なるため、工程表へ足してはいけない。

## 3. Vue SSRで描画するものが異なる

#2もVue SSRを使う。通常のMarkdown本文はOx Vueプラグインが生成した`rawHtml`を`innerHTML`で埋め込み、Appは最小のheader/mainを描画する。採用バージョンの配布コードは`@ox-content/vite-plugin-vue@3.4.3/dist/index.mjs`の`generateVueSFC`で確認した。

#1は[Markdown.vue](ox-native/Markdown.vue)の`MDCRenderer`で本文のASTをたどり、各ノードやProse部品をVueとして描画する。さらに[PortApp](nuxt-compat/PortApp.vue)・元のレイアウト・ナビ・目次・前後リンク・各コンポーネントが入る。[registry](nuxt-compat/registry.ts)と[FullSurface](nuxt-compat/FullSurface.vue)は多数の既存部品・ページをまとめて読み込む。

結果としてSSRは#1全件で7.76秒、同じMarkdown URLに限っても7.29秒、#2のMarkdown部分は0.093秒だった。**Vue SSRを採用すること自体より、本文全体を細かいVue/MDCノードとして再描画する設計の差が大きい。**

## 4. アセット参照とpayloadにも改善余地がある

追加CPU run（55.29秒、通常中央値には不算入）では、同じclient entryのCSS参照・manifest取得を1,991ページで繰り返す区間が**2.554秒**、HTML文字列の組立区間が**0.695秒**だった。残りはentry検索等の周辺処理で、親のHTML/asset区間は3.429秒。`ctx.assets.stylesheets()`は呼出しごとにmanifestのキー探索等を行い、CPU上でも`manifestKey`・パス正規化が見える。同じbuild・同じentryの参照結果を使い回す候補がある。

全HTMLは#1が277,839,194 bytes、#2が9,093,602 bytesだった。既存レイアウトのHTMLに加え、#1は言語辞書・ナビ等のhydration用payloadを各ページへ埋め込む。例えば日本語noteページはpayloadだけで約70.5 KB、そのうち辞書約36.9 KB、ナビ約28.9 KBだった。Markdown本文ASTの大部分と前後記事のbodyは既にpayloadから除いており、この残りにも共有データがある。[代表payloadの内訳](results/native-comparison/2026-10-31/payload-samples.json)。

## 5. メモリとGC

全件互換版のピークRSS中央値は約3.62 GiB、#2は約0.64 GiBだった。別途採取したNode CPUサンプル55.284秒のうち、GCのself samplingが**10.100秒、約18.3%**を占めた。GCは各工程の内側に含まれ、この10秒をwall-clock表へ追加してはいけない。子プロセスのCPUはこのサンプルに含まれない。

上位サンプルにはUnoCSSのmatch/parse、MDC側のvfile処理、Shiki/OnigurumaのWASM、Viteのモジュール評価も出ている。本文ASTと多数のモジュールを重複して持つ現状と整合するが、今回の省略実験だけでGCの全てを特定の1処理へ帰属させることはできない。CPU runでは外部のcontributors APIがHTTP 200（約0.35秒）だった。

## 改善するなら

優先度は次の順と考える。今回、通常の移植コードへ高速化変更は加えていない。

1. **通常のMarkdown本文でOxのHTML出力を保つ。** Vue/MDCを必要なカスタム部品や動的な箇所へ限定する。Proseのコードコピー・画像・リンク等の動作も含め、既存30ページVRTで段階的に確認する。#2の最小テーマをそのまま既存テーマへ差し替えるだけで互換性が成立するとは限らない。
2. **解析結果を経路間で共有する。** 本文・メタデータ・TOC・MDC/Shiki処理を別々に繰り返さず、原稿とオプションをキーに再利用する。現在のASTには後からID等を付ける処理があるため、共有時の可変状態も整理する。
3. **クライアントへ送る情報と依存を絞る。** 本文全体のASTではなく必要な部品の情報を渡し、言語辞書・ナビを共有化する。全コンポーネント登録・全ページのeager importも、必要な部品へ分割する。
4. **同一アセットの解決結果をbuild単位で再利用する。** 今回の約2.6秒の小区間が対象で、全体の約49秒の差の一部である。

これらの改善幅は、クライアント生成省略の診断を除いて未実測。既存の全機能・全1,991 URLを保ったまま4〜5秒になる、という結論にはしていない。両案は同じOx/Vite/Vueを使っており、今回の計測は追加した互換パイプラインの重複を減らす方向を支持している。
