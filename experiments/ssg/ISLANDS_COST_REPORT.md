# 5秒のPR #2から25秒の互換版へ増えた処理の診断

増加の中心は、**既存UIを支えるクライアントビルド、MDC/Shiki等の原稿互換処理、ナビを含むUI生成**だった。同じrunner・同じ依存で測り直すとPR #2は中央値4.22秒、互換版は23.79秒、差は19.58秒。URL出力数だけを減らした差は1.68秒で、ページ数の増加だけでは説明できない。

本番用・VRT合格済みの移行コードは変更せず、独立コピーにだけ診断フックと省略スイッチを挿入した。最適化は実装していない。各3回＋CPU用1回＋最後の通常構成3回、**合計25回の生成と検証が成功**した。

## 増加19.58秒の工程別内訳

総時間が中央値だった実際の1回を比較する。各区間は重ならず、合計が総時間に一致する。

| 工程 | PR #2 | 互換版 | 差 |
| --- | ---: | ---: | ---: |
| Vite起動・クライアントJS/CSS生成 | 1.49秒 | 7.56秒 | +6.07秒 |
| サーバー側の依存ロード・初回変換 | 0.09秒 | 2.28秒 | +2.19秒 |
| 原稿・互換データ準備 | 0.28秒 | 6.32秒 | +6.04秒 |
| ページ生成・payload準備 | 2.15秒 | 6.98秒 | +4.84秒 |
| 最終HTML出力・終了処理 | 0.21秒 | 0.64秒 | +0.43秒 |
| 合計 | **4.22秒** | **23.79秒** | **+19.58秒** |

工程の差であり、独立した機能ごとの純粋な追加コストではない。特にPR #2のMarkdownモジュール読込・変換はページ生成側に含まれ、互換版では原稿準備側に移っている。下の処理を外す比較と合わせて判断する。

| 診断構成 | 3回の実測（秒） | 中央値 |
| --- | --- | ---: |
| 互換版・全件 | 23.48 / 24.01 / 23.79 | **23.79秒** |
| 互換版・全件（最後に再測定） | 24.65 / 24.65 / 24.80 | **24.65秒** |
| PR #2・最小テーマ | 4.38 / 4.13 / 4.22 | **4.22秒** |
| 出力だけ同じ1,342 Markdown URLへ限定 | 22.11 / 22.02 / 22.22 | **22.11秒** |
| クライアントJS/CSSを省く | 18.26 / 18.09 / 17.82 | **18.09秒** |
| フレーム・Vue UI・固定ページ等を省く | 17.84 / 17.82 / 17.78 | **17.82秒** |
| コードハイライトだけを省く | 21.55 / 23.09 / 23.32 | **23.09秒** |
| 本文ProseAだけ単純aタグへ置換 | 24.36 / 24.73 / 24.09 | **24.36秒** |

これらの省略構成は表示や機能を落とした**原因調査専用**で、VRT合格案ではない。省いた差にはGC、アセット量、処理順の相互作用も含まれ、差を合計しない。最後の通常構成は24.65秒で、最初の23.79秒より0.86秒長かった。小差の有意性を確定する計測ではない。

### 1. クライアントJS/CSS生成：省くと約5.7秒短縮

全件のデータ準備・HTML描画を維持し、クライアントエントリーだけ微小なCSS importへ置き換えると、23.79秒から18.09秒へ短縮した。互換版には全件用Vueレジストリ、固定ページの分割チャンク、UnoCSS、既存SFC/CSS modules、Sass、PostCSS、SVG変換などが加わっている。

PR #2のJSは1 byte、互換版は29ファイル・1,638,385 bytes。互換版のCSS出力は184,021 bytes。通常MarkdownのJSモジュールは互換版でも0件なので、前の「Markdownごとに大量のJSを作る」問題は今回の主因ではない。Vue/CSS関連の非同期transform時間を合算すると実時間を超えるため、個々のプラグインに秒数を分配していない。

### 2. UIの生成：省くと約6.0秒短縮、サイドバーが約3.3秒

通常Markdown本文、head/payload、クライアントビルドを残し、`fullTheme`によるフレーム・Vue UI・YAML/固定ページ描画を省くと17.82秒になった。通常構成の`host.theme`は5.31秒で、Vue補助部品の中では以下が大きい。

| 部品 | 呼び出し | renderToStringの合計 |
| --- | ---: | ---: |
| DocsAsideNav | 1,365回 | **3.28秒** |
| GNav | 1,365回 | 0.55秒 |
| ProseA（本文のリンク） | 5,053回 | 0.27秒 |

サイドバーは再帰的なVue部品で、閉じた枝にも`v-show`を使うため、隠れた枝のDOMも各ページで繰り返し生成する。現在URLに応じた展開・強調表示があり、そのまま全ページ共通HTMLとしてキャッシュすることはできないが、静的な枝と現在地依存部分を分ける余地がある。

本文ProseAを単純HTMLへ置換すると、本文生成区間は0.84秒から0.55秒へ減った。一方、総時間の中央値は24.36秒で、最初の通常構成との差から高速化を確認できなかった。時間変動に比べて小さく、優先対象にはしない。MFM等の個別islandもサイドバーより小さい。

### 3. 原稿互換処理：約6.3秒の準備工程、その中心がMDC/Shiki

全Markdown1,434件とYAML156件を準備する。中央値の通常runでは以下を観測した。親子の重なる工程を含むので合計しない。

| 準備内の工程 | 実測 |
| --- | ---: |
| Markdown解析・メタデータ生成（親工程） | 5.58秒 |
| MDC snippetsの解析・Shiki（各原稿のPromise.all待ち） | **3.55秒** |
| Ox HTML→HAST→互換の木、目次、style等の組立 | **1.25秒** |
| 原稿ファイル読込1,590件 | 0.47秒 |
| コレクションマニフェスト | 0.07秒 |
| YAML内MarkdownのMDC処理 | 0.08秒 |
| ナビ・翻訳準備 | 0.02秒 |

Shikiのhighlightプラグインだけを外すと、MDC snippetsの待ち時間は3.55秒から中央値1.45秒へ減り、**この区間で約2.1秒**の追加コストを確認できた。総時間の中央値は23.09秒で、最初の通常構成との差は0.70秒、最後の通常構成との差は1.56秒。他工程の変動もあるため「Shikiを外せば全体が必ず2.1秒速い」とは扱わない。

MDC呼び出しは4,970 snippets（コード2,274、部品2,696）。コードの原稿文字列は442種類、全snippetsでは1,541種類しかなく、同一内容を繰り返し解析している。解析結果やハイライト結果のキャッシュを検討する根拠になるが、実際の短縮は未測定。キーには原稿だけでなくテーマ・文法・parser設定を含め、木の後続変更を考慮する必要がある。

既存profileの`native.rustTransform`は、この方式では事前生成済みHTMLを渡す区間なので、Rust本体の処理時間ではない。Oxの公開Markdown APIの内部Rust処理だけを直接切り出した計測ではない。また並行する4,970個のMDC呼び出し時間を合計すると約58.1秒にもなるが、これは重複時間でありSSG時間へ加算しない。

### 4. 対象URL追加：出力・描画だけなら約1.7秒

1,991 URLから#2と同じ1,342 Markdown URLへ絞ると22.11秒だった。URL集合の一致も検証した（#2だけ索引1件が追加）。このケースでは全1,434 Markdown/YAML準備と全件用クライアントは維持しているため、**649 URLの追加描画・出力による差**を主に見る実験である。全件対応のために増えた原稿準備や依存まで取り除いた値ではない。PR #2では同じ原稿を共有する言語URLもあるため、Markdownモジュールの実変換は1,247件だった。

通常Markdown本文のHTML化は全件合計0.84秒、JSON.stringifyは0.36秒、最終HTML出力・終了処理は0.64秒。ここを最初の最適化対象にする根拠は小さい。contributors APIは実取得し、今回の各runでは約0.05〜0.50秒で、約20秒の増加の主因ではなかった。

## 次に試す順番

1. **MDC/Shikiの同一snippetキャッシュ**：入力4,970件に対し1,541種類、コードだけなら2,274件に対し442種類。表示を変えずに重複処理を減らす案を、既存30ページVRTで確認する。
2. **サイドバーの繰り返し描画を減らす**：静的なナビ構造と現在地・開閉状態を分け、共通部分の再利用を試す。Vueから外す場合も既存DOM/CSS/操作を保つ。
3. **クライアント/SSRレジストリを必要な部品へ絞る**：現在は全件用レジストリが広く、サーバー依存ロードにも2.28秒使う。ビルド時だけの補助部品、対話部品、固定ページを分け、不要な依存の初回変換とJS/CSS生成を減らす。

この順番は、速度効果だけでなく表示互換を保ちやすい順を含む。具体的な達成時間は、最適化後のVRTと同条件のSSG再計測で確認する。

## 条件・証拠・限界

- 対象コミットは互換版`6cbe059c5d3b358557f6493b606f196c2ca06e8a`、PR #2は`c52b733c227aaf5f91341544aebe4c3977800cee`。
- Node22.22.2 / Apple M1 Pro / darwin-arm64、通常Vue、同一lockfile。元原稿・public・Vue部品・ページ・レイアウト・翻訳・既存assetsのハッシュ一致を確認。islands案にだけNuxt prepareが生成する空の`i18n-members.ts`があり、例外として記録した。
- `buildSeconds`はVite import前からawaitしたbuild完了まで。PNPM/Node起動と検証は除外する。前回の**5.37秒／25.07秒とは境界が違う**ため、今回の4.22秒／23.79秒同士で比較する。
- 新規プロセスで順次実行、OSキャッシュは保持。原稿・実装のハッシュを各run前後に検証。VRTや他のビルドとは同時実行しない。ソース修正や基準画像更新は行わず、VRTを再実行していない。
- 全25回で出力件数とHTMLの構造を確認。no-theme以外は元のverifierも計測外で成功。省略構成はブラウザー互換性を保証しない。
- CPUプロファイルは追加1回、26.43秒。GC self sampleは3.04秒（約11.5%）で、既存工程に含まれる。別工程として足さない。自プロセスのV8サンプルで子プロセスのCPUは含まない。
- 各3回・固定順の探索的診断で、微小差の統計的有意性は評価しない。最後の通常構成で0.86秒の変動を確認。処理省略によるメモリ/GC/キャッシュ等の相互作用がある。
